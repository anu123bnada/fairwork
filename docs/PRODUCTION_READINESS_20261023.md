## Scope and distinctions

Inventory covered Next.js routes/components/server services, Supabase migrations/configuration, Gemini adapter/consent, test suites and scripts, CI/configuration, documentation, assets and `mobile/poc` Android configuration/source. Sensitive environment files and backup contents were not dumped. Existing broad untracked work and the pre-existing README modification were preserved. Local Next.js 16.4.1 guides on proxy/cookies were read before code edits.

The product is not universally a mock: `src/server/offer.ts`, `agreement-workflow.ts`, `work.ts`, `work-integrity.ts`, `work-cases.ts`, `passport-sharing.ts` and identity/organization services use authenticated Supabase RPCs. `src/components/fairwork/product-app.tsx:469` routes normal work/passport/employer views to functional components; preview placeholders are separate. `src/server/offer-store.ts` is a guarded legacy local demo store and rejects production; its existence does not prove primary workflows use filesystem persistence. Session storage holds an offer selection identifier, not the durable work ledger.

Registration confirmation and recovery clients expect `token_hash` (preferably in a fragment): `src/components/fairwork/registration-form.tsx`, `src/components/fairwork/recovery-form.tsx`. Hosted email templates, delivery and redirect allowlists were not inspected; they remain acceptance requirements, not confirmed defects.

Android-specific additional evidence: `mobile/poc/www/index.html` states that the bundle contains no authentication/agreement implementation; it depends on the Next.js server. `mobile/poc/android/app/src/main/AndroidManifest.xml` declares only the launcher intent filter, with no HTTPS app-link callback. Removing `server.url` alone would therefore ship the placeholder, and native email-link/session handoff needs explicit implementation and testing.

## Repair and final verification

Implemented only in `src/app/api/v1/auth/sign-in/route.ts`, with regressions in `tests/unit/auth.test.ts`. All account-access failures now attempt local-session sign-out, including rejected RPC promises. Returned or thrown cleanup failures produce a generic 503. Disabled-account denial remains 403 when cleanup succeeds; successful sign-in and UI/design are unchanged.

Residual limit: this attempts provider cleanup; it cannot guarantee remote revocation when the provider itself is unavailable. Existing SQL authorization/account-state enforcement remains essential. No tokens or provider diagnostics are returned.

Post-fix unit suite: **40 files / 222 tests passed**, including the two regressions, in `test-results/production-audit-unit-after.log`. Additional verification is recorded below when completed. The release decision remains NO-GO regardless of this bounded fix.

- `npm run typecheck`: passed after repair (`test-results/production-audit-typecheck.log`).
- Separate integration run: **11 files / 146 passed / 17 skipped** (`test-results/production-audit-integration.log`). These exercised disposable PGlite databases, not hosted data. Skipped cases require native PostgreSQL sessions/concurrency; this audit did not run their native runners.
- Focused authentication suite after the final lint correction: **9 passed** (`test-results/production-audit-auth-after.log`). The lint correction replaced an intermediate generic Error with the existing sanitized AppError; API behavior is unchanged.
