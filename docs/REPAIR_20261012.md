## Participant recovery

The new `api.get_agreement(request jsonb)` accepts only `{offerId}` and returns a
fixed projection of the latest manual terms, questions, attributed answers, the
caller's confirmation, eligibility and a common agreement ID. It does not expose
raw uploaded/pasted source, private receipts, arbitrary records or a directory.
The HTTP mapping is `GET /api/v1/agreements?offerId=UUID`; successful/error responses
are private/no-store and the route authenticates the session before the RPC.

The SECURITY DEFINER owner remains `fw_user_exec`, with an empty search path,
FORCE RLS, no bypass role and existing narrow private-table privileges. Effective
EXECUTE is tested for authenticated/anon/service_role/PUBLIC. No managed Auth
grant or ownership changes are needed. The restricted local migration-role
fixture executes the new migration. PostgreSQL 17 uses the SQL features present
here; execution evidence is local PGlite, not a hosted PostgreSQL 17.11 run.

Reads share the existing per-user identity read budget of 120/minute. The saved
offer row's UUID supplies a stable candidate agreement ID before either person
confirms; an existing persisted agreement ID takes precedence. Reads serialize
with offer commands and return the current revision. Client confirmation resolves
that ID again and refuses a version/hash different from the displayed revision.
Existing SQL checks still enforce the frozen participant and current authority.

The app stores only a selection ID in session storage. It reloads all terms,
answers and confirmations from the authenticated server; browser storage never
establishes authority or agreed content. Home and an empty agreement view accept
a saved offer ID. The participant path opens the same saved record in a separate
session; it is an ordinary authenticated record reference, not bearer access.
After signing in, reopen that path. A reload button refreshes the other person's
decision. Failed loads clear the displayed offer and fail closed.
